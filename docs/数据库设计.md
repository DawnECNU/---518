# MongoDB 数据库设计（阶段一）

本文件说明阶段一问卷系统的 MongoDB 数据模型、集合关系、索引、数据库校验和设计取舍。数据库设计的代码实现位于：

- `backend/schema.py`：定义集合和文档校验规则；
- `backend/db.py`：连接 MongoDB、安装校验规则和创建索引；
- `backend/app.py`：执行实际查询、插入和更新；
- `backend/survey_logic.py`：构造题目、跳转规则和统计数据。

## 1. 集合划分

数据库 `survey_phase1` 包含四个集合：

| 集合 | 作用 | 增长特点 |
| --- | --- | --- |
| `users` | 用户账号 | 小规模、稳定增长 |
| `surveys` | 问卷元数据 | 每个用户少量 |
| `questions` | 题目、选项、校验限制、跳转规则 | 每题一个文档 |
| `responses` | 一次填写过程及最终答卷 | 数量最大，持续增长 |

没有把所有内容塞进一个文档，也没有使用关系数据库。四个集合分别对应独立生命周期：问卷结构在发布时锁定，答卷在发布后持续增长，二者适合分开存储。

## 2. 文档结构

### users

```json
{
  "_id": "ObjectId",
  "username": "alice",
  "password_hash": "scrypt:...",
  "created_at": "Date",
  "schema_version": 1
}
```

`username` 有唯一索引。密码只保存加盐哈希。

### surveys

```json
{
  "_id": "ObjectId",
  "owner_id": "ObjectId",
  "title": "校园生活调查",
  "description": "问卷说明",
  "allow_anonymous": true,
  "allow_multiple": false,
  "status": "draft | published | closed",
  "public_id": "随机公开标识",
  "created_at": "Date",
  "updated_at": "Date",
  "deadline": "Date | null",
  "published_at": "Date | null",
  "closed_at": "Date | null",
  "schema_version": 1
}
```

使用 `owner_id` 引用用户。公开链接使用短随机 `public_id`，而不是直接暴露 ObjectId。

### questions

```json
{
  "_id": "ObjectId",
  "survey_id": "ObjectId",
  "order": 1,
  "type": "single | multiple | text | number",
  "title": "你的性别",
  "required": true,
  "options": [
    {"key": "A", "label": "男"},
    {"key": "B", "label": "女"}
  ],
  "constraints": {
    "min_selections": null,
    "max_selections": null,
    "exact_selections": null,
    "min_length": null,
    "max_length": null,
    "min_value": null,
    "max_value": null,
    "integer_only": false
  },
  "jump_rules": [
    {
      "_id": "ObjectId",
      "condition": {"kind": "option_equals", "value": "A"},
      "target": "ObjectId | null",
      "created_at": "Date"
    }
  ],
  "created_at": "Date",
  "updated_at": "Date",
  "schema_version": 1
}
```

题目独立成文档，主要原因是：

- 统计和填写时可按 `survey_id` 查询，不必加载整份问卷；
- 单题修改不会重写整个问卷文档；
- `(survey_id, order)` 唯一索引保证顺序；
- 题目文档大小受控，跳转规则随题目保存，读取题目时即可完成跳转判断。

选项使用 `key + label`。`key` 是稳定的 A/B/C 标识，跳转规则引用 `key`，因此修改选项文字不会破坏规则。

### responses

```json
{
  "_id": "ObjectId",
  "survey_id": "ObjectId",
  "user_id": "ObjectId",
  "anonymous": true,
  "status": "in_progress | submitted",
  "answers": {
    "题目 ObjectId 字符串": "A",
    "另一题 ObjectId 字符串": ["A", "C"]
  },
  "path": ["已访问题目 ObjectId"],
  "current_question_id": "ObjectId | null",
  "started_at": "Date",
  "updated_at": "Date",
  "submitted_at": "Date | null",
  "schema_version": 1
}
```

设计说明：

- 一份答卷一个文档，天然隔离不同填写者，支持多人并发。
- `answers` 使用题目 ID 作为动态字段，答一题只 `$set` 一个字段，写入简单且原子。
- `path` 记录实际访问过的题目，被跳转跳过的必答题不会误判为漏答。
- `current_question_id` 保存断点，使未提交答卷可以继续填写。
- 只有 `status = submitted` 的答卷进入统计。
- 匿名问卷仍保留 `user_id` 用于登录校验、断点恢复和重复填写限制；对外统计不读取或展示该字段。

## 3. 跳转规则

`condition.kind` 支持：

| kind | 适用题型 | 含义 |
| --- | --- | --- |
| `option_equals` | 单选 | 选中指定选项 |
| `option_contains` | 多选 | 选中项包含指定选项 |
| `selection_count` | 多选 | 选择数量 `eq/gte/lte` 某个值 |
| `number_range` | 数字 | 数值落在闭区间 `[min, max]` |

规则按数组顺序求值，第一条命中规则生效。目标必须位于当前题之后，或为 `null`（结束问卷）。这种约束在发布前校验，运行时不会形成循环。

## 4. 索引

| 集合 | 索引 | 用途 |
| --- | --- | --- |
| `users` | `username` 唯一 | 登录、防重名 |
| `surveys` | `(owner_id, created_at desc)` | 用户问卷列表 |
| `surveys` | `public_id` 唯一（仅字符串） | 公开链接查询 |
| `questions` | `(survey_id, order)` 唯一 | 按顺序加载题目、保证题号唯一 |
| `responses` | `(survey_id, status)` | 统计已提交答卷 |
| `responses` | `(survey_id, user_id, status)` | 重复填写检查、断点恢复 |
| `responses` | `(user_id, updated_at desc)` | 用户最近答卷 |

## 5. 数据库级校验

`schema.py` 为四个集合定义 `$jsonSchema`，应用启动时通过 `create_collection` / `collMod` 安装：

- 必填字段；
- 字段 BSON 类型；
- 问卷状态、题目类型、答卷状态枚举；
- 题号最小值；
- 选项数量上限；
- `schema_version`。

即使绕过 Flask 直接写数据库，不合法文档也会被 MongoDB 拒绝。`validationAction = "error"`。

## 6. 为什么适合 MongoDB

- 题目的选项和跳转规则是天然嵌套结构，放在题目文档中读取一次即可使用，不需要多表关联。
- 答案集合按键值形式保存，不同题型答案分别是字符串、数组、数字，文档模型可直接容纳。
- 答卷量会持续增长，而问卷结构在发布后锁定，读写模式清晰。
- 通过 `path` 和支持动态字段的 `answers`，跳转与断点恢复实现简单。
- `schema_version` 为第二阶段需求变化预留迁移入口。

## 7. 为什么不用关系数据库结构

关系模型通常需要 `surveys`、`questions`、`options`、`jump_rules`、`responses`、`answers` 等多张表，并通过多次 JOIN 还原一份问卷或统计结果。阶段一的数据读取以“整题 + 规则”和“整份答卷”为单位，文档聚合更贴合访问方式；同时 MongoDB 的 JSON Schema、唯一索引和原子更新已能满足一致性要求。

## 8. 集合关系

```text
users
  _id ◀────────────── surveys.owner_id
                         │
                         │ surveys._id
                         ▼
                     questions.survey_id
                         │
                         │ questions._id
                         ├────────────▶ questions.jump_rules.target
                         │
                         ▼
users._id ◀────── responses.user_id
                         │
                         │ responses.survey_id
                         ▼
                       surveys._id
```

关系说明：

| 关系 | 保存方式 | 说明 |
| --- | --- | --- |
| 用户 → 问卷 | `surveys.owner_id` | 一个用户可以创建多份问卷 |
| 问卷 → 题目 | `questions.survey_id` | 一份问卷包含多道题 |
| 题目 → 跳转目标 | `questions.jump_rules.target` | 目标为另一道题的 `_id` 或 `null` |
| 用户 → 答卷 | `responses.user_id` | 用于登录校验、草稿恢复和重复填写判断 |
| 问卷 → 答卷 | `responses.survey_id` | 一份问卷对应多份答卷 |

MongoDB 不提供关系数据库那种外键自动约束。`owner_id`、`survey_id` 等字段只保存 ObjectId，引用对象是否存在、是否属于同一用户，由后端业务逻辑检查。

## 9. 引用与嵌入的选择

### 9.1 为什么题目单独作为集合

- 题目数量和题目内容可能持续增加；
- 问卷列表页不需要加载所有题目；
- 填写时只按 `survey_id` 读取当前问卷的题目；
- 单题修改不需要重写整份问卷文档；
- `(survey_id, order)` 唯一索引可以保证题号不重复。

### 9.2 为什么选项、限制和跳转规则嵌入题目

`options`、`constraints` 和 `jump_rules` 有以下特点：

- 数量有明确上限；
- 总是与题目一起读取；
- 没有独立查询需求；
- 跳转规则需要引用本题的选项 key。

因此把它们嵌入题目文档，可以做到“读取一道题即可完成校验和跳转判断”，减少集合访问次数。

### 9.3 为什么答卷必须独立

答卷数量会随填写人数持续增长。如果把答卷嵌在问卷或题目文档中，会导致：

- 问卷文档不断增大；
- 多人同时填写时竞争同一个文档；
- 达到 MongoDB 单文档大小限制的风险；
- 统计和查询需要加载大量无关内容。

一份答卷一个文档可以自然隔离不同填写者，并且允许按 `survey_id + status` 高效统计。

## 10. 典型查询与索引对应关系

| 业务操作 | MongoDB 查询或更新 | 使用索引 |
| --- | --- | --- |
| 登录 | `users.find_one({username})` | `uniq_username` |
| 查询我的问卷 | `surveys.find({owner_id}).sort({created_at:-1})` | `owner_created` |
| 打开公开链接 | `surveys.find_one({public_id})` | `uniq_public_id` |
| 加载题目 | `questions.find({survey_id}).sort({order:1})` | `survey_order` |
| 统计问卷 | `responses.find({survey_id,status:"submitted"})` | `survey_status` |
| 检查重复填写 | `responses.count_documents({survey_id,user_id,status:"submitted"})` | `survey_user_status` |
| 恢复最近答卷 | 按用户和更新时间查询 | `user_updated` |

索引不是越多越好。当前索引只覆盖高频访问路径，并为用户名和公开链接提供唯一性约束。

## 11. 数据生命周期

### 11.1 用户

注册时新增，登录时读取，用户 ID 被问卷和答卷引用。系统没有实现用户删除，因此暂不需要级联删除逻辑。

### 11.2 问卷

`draft` 阶段允许配置题目；`published` 后结构锁定；`closed` 后不再接受答卷。状态字段和多个时间戳共同表达生命周期：

```text
created_at
  ↓
draft
  ↓
published_at + published
  ↓
deadline 到期或 closed_at + closed
```

### 11.3 题目

题目在草稿阶段新增和编辑，发布后锁定。题目 ID 同时被以下位置引用：

- 答卷 `path`；
- 答卷 `answers` 的字段名；
- 跳转规则的 `target`。

当前阶段没有题目删除功能，且发布后题目结构锁定，因此这些引用在阶段一不会悬空。

### 11.4 答卷

`in_progress` 表示可以继续填写；`submitted` 表示最终提交。提交后 `submitted_at` 不为空，并进入统计集合查询范围。

## 12. 答案对象的建模

`answers` 使用动态字段：

```json
{
  "66f0...题目1": "A",
  "66f0...题目2": ["A", "C"],
  "66f0...题目3": "这是一段文本",
  "66f0...题目4": 35
}
```

优点：

- 不需要为每种题型建立不同集合；
- 更新某题时可以直接 `$set` 对应字段；
- 查找某题答案时不需要扫描数组；
- 支持单选题、多选数组、文本和数字等不同值类型。

字段名使用题目 ObjectId 的十六进制字符串。由于问卷发布后题目结构锁定，已提交答卷中的字段不会失去对应题目。

## 13. 并发控制

不同填写者各自拥有独立的 `responses` 文档，因此不会互相覆盖。

同一份答卷在不同页面同时作答时，答案更新使用条件更新：

```python
{
  "_id": response_id,
  "user_id": user_id,
  "status": "in_progress",
  "current_question_id": current_question_id
}
```

只有仍停留在当前题目且状态未提交的更新才会成功。这样旧页面不能覆盖已经前进后的题目状态。

## 14. 一致性边界

- 用户名唯一性由 MongoDB 唯一索引保证。
- 公开链接唯一性由 `public_id` 唯一索引保证。
- 题号唯一性由 `(survey_id, order)` 唯一索引保证。
- 问卷发布后结构不可修改，保证历史答卷与题目结构一致。
- 业务校验在 Flask 中完成，数据库校验负责字段结构和枚举。
- 当前项目运行在单机 MongoDB 上，没有使用多文档事务；核心更新尽量设计为单文档原子操作。

## 15. Schema 校验的边界

`schema.py` 的 `$jsonSchema` 校验：

- 必填字段是否存在；
- 字段 BSON 类型；
- 字符串长度；
- 枚举值；
- 数值最小值；
- 数组元素结构。

它不负责：

- 用户是否真的拥有该问卷；
- 跳转目标是否在当前题之后；
- 必答题是否已经回答；
- 多选题是否满足数量限制；
- 统计应该使用哪些答卷。

这些属于后端业务规则，必须在 `backend/app.py` 和 `backend/survey_logic.py` 中实现。

当前 Schema 没有设置 `additionalProperties: false`，因此允许文档扩展额外字段；这是为后续阶段迁移预留空间。

## 16. 第二阶段扩展

每份文档都有 `schema_version = 1`。第二阶段修改数据结构时可使用版本号识别旧文档，常见扩展方式包括：

- 增加可选字段而不破坏旧文档；
- 对旧版本文档执行批量迁移；
- 保留旧字段并增加新字段的兼容读取；
- 在应用启动时逐步升级 Schema 校验规则。

如果第二阶段需要题目复用、题目银行或跨问卷统计，可继续保留现有四个集合，并新增独立题目模板或统计索引，无需推翻当前结构。

## 17. 已知限制与改进方向

- 当前没有多文档事务，跨集合操作通过流程顺序和发布锁定保证一致。
- 没有题目删除和重排功能，避免破坏题目引用。
- 匿名问卷仍保留内部 `user_id`；严格匿名场景应改用匿名令牌。
- 统计在应用层计算，适合课程规模；超大数据量可改为 MongoDB 聚合管道或预聚合集合。
- 跳转仅支持向后，不支持循环和回跳。
